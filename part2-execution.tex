%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\part{The Execution Layer}\label{part:execution}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Part~\ref{part:protocol} described infrastructure that proves that a given asset state is spent exactly once. This guarantee supports most blockchain applications, including issued currencies, non-fungible assets, programmable ownership, automated market making, and bridges to external chains. These applications do not require a globally shared state machine.

\section{Tokens}

A token is a self-contained ledger containing its genesis, complete transfer sequence, and certificates proving that each transfer was recorded exactly once. A recipient establishes validity by checking these records against the trust base, without consulting external state. A wallet can therefore run in a browser tab, and verification can be performed offline.

\subsection{States and Identifiers}

A token state is a spending condition together with a hash linking it to the token's history. The \emph{state identifier} is derived from that pair, and it is the key the aggregation layer records when the state is spent. Each transfer introduces fresh randomness into the next state hash, so the next state identifier is unpredictable to anyone who has not seen the transaction. The aggregation layer therefore cannot connect one spend of a token to the next, even though it records both.

The network observes a sequence of apparently unrelated identifiers. It receives no amounts, asset types, owner details, or links between spends of the same token.

\subsection{Minting and Issuance Authority}

The minting key pair is a public constant of the protocol. Anyone can construct a syntactically valid mint transaction. A certified mint proves only that the token identifier was fresh; it confers no issuance authority.

Issuance authority is established by two genesis fields that every subsequent recipient rechecks.

The token type classifies the token and specifies its permanent rules. A type definition fixes payload decoding, admissible minting justifications, and issuance policy. A published definition is immutable. Every verifier must apply byte-identical rules indefinitely to prevent different recipients from reaching different validity decisions for the same token.

The mint reason justifies the mint under the type's rules. It can be an issuer's authorization signature, a value-conservation proof for change from a split, a proof of a matching asset locked on an external chain, or a zero-knowledge proof of any statement accepted by the type.

Recipients enforce issuance rules during verification. Validators may include a counterfeit mint, but recipients reject it because it fails the required checks. This fail-shut behavior is mandatory on the public network. A verifier must reject a token if its type is unknown, its reason format is unregistered, or its reason is inadmissible for its type. Such tokens cannot be accepted as unvalidated.

\subsection{Issuance Mechanisms}

\begin{description}
    \item[Native issuance.] An issuer defines a type pinning its own key and authorizes each mint with a signature. This is the ordinary case for a currency or a collection.

    \item[Derived issuance.] A token can represent change from a split. A split burns a source token and mints outputs whose combined value provably equals the source value. A merge performs the reverse operation. In both cases the reason is a conservation proof governed by a network-wide rule, independent of the issuer.

    \item[Bridged issuance.] The reason is a proof that a matching amount is locked in a vault on another chain, checked by every recipient against that chain's own consensus. Section~\ref{sec:bridging} covers this in full.

    \item[Proof-carrying issuance.] The reason is a succinct proof of an arbitrary statement defined by the type. Any statement that a verifier can check in constant time can authorize a mint.
\end{description}

\subsection{Value, Splitting, and Conservation}

A fungible token carries a collection of assets, each an identifier and a non-negative amount. Splitting divides it while preserving every enclosed asset independently.

The construction is a sum tree. The owner allocates the source value across the intended outputs, builds one tree per asset identifier whose leaves are the outputs and whose root commits to the total, and then burns the source token in a transfer whose data is exactly that commitment. Each output is then minted carrying the burned source token and an inclusion proof against the committed allocation.

A verifier of any output re-derives its commitment from the mint fields and verifies inclusion in the allocation tree. It also requires the tree's committed total to equal the source token's amount. The recipient checks value conservation independently of the wallet that performed the split. A recipient learns the source amount, verifies the source token completely, and accepts only if no value could have been created.

Across the platform, negligence can destroy value but cannot create it. Burning a source token and then losing the data needed to mint an output destroys that output's value. No party can inflate the supply.

\section{Transaction Flow and Latency}

A transfer involves three parties and one round trip to the network. The recipient supplies the spending condition under which it wishes to receive the token. The sender builds the transaction, satisfies the current condition, and asks the aggregation layer to record the state being spent. The layer returns a proof. The sender passes the token, now extended by one transfer and its proof, to the recipient, who verifies it.

Settlement is final when the proof is issued, in one to two seconds. For workloads requiring lower latency, the protocol supports a second ordering of the same steps.

In the low-latency path, the sender delivers the token and transaction directly to the recipient, who submits the request. The layer immediately confirms that the state has not been spent and is scheduled for recording. The recipient can then release goods: only the sender could have spent the state previously, and the recipient now controls the request. The inclusion proof follows in the next round and is required before the token is treated as spendable inventory. With sufficient inventory to cover the round time, a participant can transact continuously without waiting for each round.

Neither path involves a mempool, a block, a fee auction, or a confirmation depth. A party that is offline can verify a token it received an hour ago or a year ago with the same procedure and the same result.

\section{Programmable Ownership}

Ownership in Unicity can be specified by a \emph{predicate}, an arbitrary rule determining when a token may be transferred. Predicates generalize public-key ownership and are evaluated off-chain by the transaction participants.

The standard set covers the usual requirements: a signature under a given key, payment to a key hash, payment to a script hash, multi-signature requiring all of a set, threshold signature requiring some of a set, a timelock that forbids transfer before a reference time, a hashed timelock combining a secret with a deadline, a burn predicate that can never be unlocked, and an open predicate that anyone may satisfy. Time-dependent predicates read their reference time from the certified round rather than from any local clock, so two verifiers always agree about whether a deadline had passed.

The \emph{STARK proof predicate} verifies a zero-knowledge proof that a committed program authorizes a particular spend under a fixed proof system and policy. The proof binds the current predicate, spending message and any required certified time; private witnesses remain hidden. Recursive verification incorporates these proofs into token-history proofs, preserving history compression~\cite{yellowpaper}.

This gives the predicate system Turing-complete expressiveness: any terminating computation can define a spending condition. With recursive compression to a fixed final proof, fixed security parameters and fixed public-input size, verification is constant in the amount of computation proved. Proving cost for the user still grows with that computation.

A reduction to unforgeability of the predicate family proves that generalizing ownership from public keys to predicates preserves three execution-layer properties. A state cannot be spent twice, only the legitimate owner can prevent a token from being spent, and the network cannot link transactions of the same token.

\subsection{Atomic Swaps}

Two parties can exchange tokens without trusting each other or any intermediary, using interlocking predicates that guarantee either both transfers complete or neither does. Correctness is enforced by the predicates themselves. There is no custodian, no escrow contract holding both sides, and no global state in which the swap is arranged.

For applications requiring agreement among several parties, the parties coordinate directly. Conditions attached to their tokens enforce the agreed outcome.

\section{Verifiable Execution}\label{sec:verifiable}

Execution is \emph{verifiable} when acceptance is a deterministic function of its output and a rule set fixed in advance and identical for every party. A recipient checks the result without relying on the producer.

Verification requires immutable rules to prevent disagreement between verifiers. Checks must be inexpensive enough for recipients to perform, and failure behavior must require rejection of unverifiable tokens rather than provisional acceptance. Verification resources must also be bounded so that malicious inputs exhaust a defined budget and are rejected without exhausting the verifier.

Unicity provides two mechanisms for verifiable execution, differing in cost. Where an application instead requires multiple parties to write to one object in a defined order, such as an order book with a single matching queue, the enshrined EVM partition of Section~\ref{sec:evm} provides a conventional execution environment certified by the same consensus layer.

\subsection{Re-Verification Against a Frozen Rule}

By default, every recipient reruns the token type's rules to check the producer's computation. This enforces issuance policies, value conservation, and type-defined state machines without consensus.

Verification work grows with the token's provenance. A worklist initially contains the received token. If verification reveals a genesis dependency on an earlier token, that token is added to the worklist; verification continues until the list is empty. A single cumulative budget limits bytes, items, nesting depth, and proof steps across the entire run. A deliberately deep or wide provenance graph that exhausts the budget is rejected as invalid. Identically configured verifiers accept exactly the same tokens.

\subsection{Zero-Knowledge Proofs}

A zero-knowledge proof replaces re-verification where re-verification is too expensive. The producer generates a succinct argument that the computation satisfies a fixed relation, and the verifier checks it at a cost independent of the work it attests to, against a verifying key pinned in advance. Unicity uses this for programmable spending, value conservation across large split allocations, token history compression, and bridge redemption, where a contract on another chain must settle a claim it could never afford to replay.

\subsection{Execution That Cannot Be Re-Checked}

Some computations are too expensive for recipients to rerun. ZK proofs establish correct execution when the computation can be expressed as a fixed relation; other assurance mechanisms introduce additional trust assumptions.

\section{Privacy}\label{sec:privacy}

Unicity limits the data submitted to the network to a state identifier and the data satisfying a spending condition. The amount, asset, sender, recipient, and token are never submitted. This privacy property therefore does not depend on encrypting or hiding submitted data, and it costs nothing to obtain.

Two consecutive spends of the same token are unlinkable to the network, because the state mask makes the next identifier unpredictable. Two residual exposures remain at the execution layer. A party holding a token can read its history. A party that transacts repeatedly under one key can be recognized by counterparties who see that key.

\subsection{One-Time Addresses}

The second exposure is removed by using a fresh spending condition for every payment. Doing so naively would require the recipient to generate, distribute, and store a new keypair per payment, and would make every transfer interactive. Unicity derives one-time addresses instead, from a single persistent secret, without interaction.

The recipient publishes one durable address. A sender generates a fresh ephemeral key and combines it with that address through Diffie-Hellman to obtain a secret that only the two of them can compute. The sender uses that secret to offset the recipient's published key into a one-time key, locks the payment to it, and includes the ephemeral public value in the transaction. The recipient recomputes the same offset from its own secret and the ephemeral value, and so obtains the private key for the one-time address. No message is exchanged in advance, and the recipient stores nothing beyond its persistent secret.

The derived offset is bound both to the ephemeral value and to the token's current state hash. This matters because the sender chooses the ephemeral key and may be adversarial. A sender that picks a predictable ephemeral value, or that deliberately leaks it, still cannot make the derived address predictable to a third party. A sender that reuses the same ephemeral value across payments still produces unrelated addresses, because the state hash differs for every transition. The recipient verifies that the sender performed the derivation correctly before treating the payment as spendable.

One-time addresses are ordinary public keys and are uniformly distributed. An observer cannot distinguish a one-time address from any other, cannot link one to the published address it was derived from, and cannot link two of them to each other. A merchant can therefore publish a single address indefinitely while every payment it receives lands somewhere unrelated.

The shared secret established by this derivation also keys encryption of the transfer payload, so the token and its accompanying data travel encrypted to the recipient over whatever channel the parties choose. The choice is per transaction and requires no support from the aggregation layer, which is not a participant in it.

The third row states the limitation that distinguishes this model from a shielded-pool design. A recipient re-executes the token's history in order to accept it, so that history is disclosed to the recipient by construction. One-time addresses remove the linkage between that history and any persistent identity: a recipient sees a chain of spending conditions without learning whose they were. Where an application needs the history itself to be withheld, provenance compression replaces ancestor tokens with a certificate, which reduces what is transmitted. That is data minimization and not a hiding guarantee, and the following section states its limits.

The fifth row is a property of applications that deliberately introduce shared state. Pool activity is visible to everyone who verifies a token the pool produced, because verification consists of rechecking the transitions. An application that requires confidential trading does not use a shared pool.

Traceability requirements can be expressed in the token type. A regulated instrument can define transfer rules enforced by every recipient, such as an attestation from an accredited party at each step. Recipients check compliance before acceptance, without requiring retrospective analysis of a public ledger. The formal treatment of the privacy properties, including the unlinkability proofs, is given in the execution-layer paper~\cite{exemodel}.

\section{History Compression}

A token accumulates one certified transaction per transfer, so an unmodified token grows with use. Compression replaces a prefix of that history with a zero-knowledge proof that the prefix was a valid, certified chain of transitions.

Compression changes the token's representation without executing a transaction, spending state, or creating state. The token identifier, genesis, and current state remain unchanged. The aggregation layer neither participates in nor observes compression. The compressed and original representations identify the same token in the same state, and spending either consumes the same state identifier. Compression requires no token-type opt-in and cannot duplicate a token.

The construction uses the append-only property established in Part~\ref{part:protocol}. One recent certificate anchors inclusion of arbitrarily old entries because tree entries are never removed. This replaces a certificate check per transfer with one certificate and a hash path per transfer. Transfer-chain validity and certification are proved as two separate ZK relations, each with its own verifying key pinned by the network. Separating them allows a holder to fold an accumulated history back to constant size rather than only appending to it.

Compression also applies to the ancestor graph. A token created by a split depends on its source, which may itself have been created by a split. Provenance compression replaces this graph with a certificate about the source alone, allowing one certificate to serve all outputs of a split.

Compression is optional and runs in the background, off the payment preparation critical path. It is lossy and irreversible: a holder that discards the original records cannot reconstruct them. This can prevent use by a future counterparty whose verifier lacks the required verification keys. Compression reduces size only above a break-even point; compressing a short history produces a larger token. Wallets should retain raw history separately and use the compressed form for transport.

\section{The Enshrined EVM Partition}\label{sec:evm}

The enshrined EVM brings Ethereum-compatible smart contracts into the same security system as Unicity's peer-to-peer tokens. Developers can use familiar contracts, wallets and tooling for applications that need shared, ordered state, while ordinary token transfers retain the execution layer's privacy and independent processing.

\begin{itemize}
    \item \textbf{One security system.} The EVM shares Unicity's validator set and certified consensus state. Contracts can authenticate token-state proofs directly, enabling transfers between the two execution models without an additional bridge committee or trusted relay.
    \item \textbf{Independent transaction capacity.} Aggregation shards operate independently of the EVM partition. EVM congestion does not impose a block-space bottleneck on unrelated peer-to-peer token transfers.
    \item \textbf{Native protocol functions.} Governance, staking and asset vaults can use Unicity certificates inside contracts. Certified locks within this partition require no external-chain confirmation wait.
\end{itemize}

This lets an application combine shared contract state with direct token settlement within one network.

\subsection{Native Currency}

UCT pays EVM gas, backs validator stake and funds rewards. Its supply is allocated at genesis, and protocol execution creates no additional currency. Staking rewards come from an existing allocation; slashing transfers collateral to the treasury. Representing UCT as a wrapped contract token or a peer-to-peer token does not increase supply, because each representation is backed by existing currency.

\section{Bridging}\label{sec:bridging}

Unicity brings external assets into its peer-to-peer economy without appointing bridge signers or giving an operator discretion over deposits. Holders can transfer those assets with Unicity's privacy and scalable transaction capacity, while recipients independently verify their backing. Withdrawal is authorized by cryptographic evidence checked by the vault contract.

\subsection{Verifiable Backing and Redemption}\label{sec:bridge-in}

To bring an asset in, a holder locks it in the external vault and creates a Unicity token tied to that deposit. Every recipient checks that the lock is final, matches the token's value and ownership, and backs only that token. A token without valid backing is rejected even if someone obtained certification for its mint. Splitting preserves the total backed value.

To redeem, the holder burns the token, fixing the external recipient and amount. A proof establishes that the token was valid and backed, and that the burn has not already been redeemed. The vault checks the evidence and pays once. A Unicity burn is final when certified, and the bridge adds no challenge period; external deposits and payouts still follow the external chain's finality rules.

\subsection{What the Holder Can Verify}

\begin{itemize}
    \item \textbf{Backing without reliance on an issuer's promise.} Recipients verify the locked assets themselves. Conservation rules prevent splits from creating additional claims on the same backing.
    \item \textbf{No privileged proof producer.} Anyone holding the necessary token data can produce a redemption proof. A proving service cannot redirect the payment, change its amount or authorize a second withdrawal.
    \item \textbf{Immutable release conditions.} The vault's verification rules are fixed at deployment. Even the deployer cannot substitute a rule that releases assets to another party.
    \item \textbf{Efficient verification.} One succinct proof can cover a batch of redemptions, with proof-verification cost independent of the histories it covers. The contract's record for preventing repeated redemption remains compact as usage grows.
\end{itemize}

These guarantees rely on sound proofs, correct vault contracts, authenticated Unicity certificates and the external chain's finality. Bridge administrators and proof producers add no authority over the holder's assets.

\subsection{Redemption Without a Proving Service}\label{sec:redemption}

The vault also supports direct verification of the same redemption conditions. Supported token types are constrained so every admitted history can be checked within the external chain's execution limits. If the succinct prover is unavailable, a holder can use this more expensive path. Redemption therefore does not depend on the continued operation of a particular proving service. A new vault version requires ordinary redemption and re-deposit, preserving the existing vault's fixed release conditions.

\subsection{Transfers Within Unicity}

The same approach connects peer-to-peer tokens with the enshrined EVM partition. Both sides share Unicity's consensus and finality, so transfers need no additional bridge committee, foreign light client or external-chain confirmation wait. UCT can move between contract-based applications and direct token payments without creating additional supply.
