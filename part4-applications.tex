\section{Stablecoins for Agentic Payments}

Bridged stablecoins are the platform's most immediate application. Stablecoins are becoming the settlement instrument for the machine economy, but their issuing chains were designed for human transaction volumes. Transfer fees vary with unrelated demand, settlement takes seconds to minutes depending on the chain and current conditions, and transaction records remain permanently available for public analysis. These properties are tolerable for payments between people but constrain API metering, data-feed settlement, and per-inference payments. Fees are usually the decisive constraint.

\medskip

Unicity provides a settlement venue for these assets while retaining the existing issuer.

The asset is locked in the vault and represented by a token minted against a backing proof checked by every recipient, as described in Section~\ref{sec:bridging}. From that point it behaves as any other Unicity token, which changes the economics of stablecoin payment in four ways.

\medskip

A payment settles deterministically in one to two seconds, so a merchant releases goods against settlement rather than against a confirmation count. Settlement is bought as a subscription, so an agent making a million small payments pays what one making a thousand pays, which is what makes per-request pricing viable at all. Transfers are private to the parties, so a business does not publish its supplier relationships and an agent does not publish its trading pattern. Recipients validate locally, without a node, a chain synchronization, or an RPC provider that observes every payment and can decline to serve it.

\medskip

Redemption is equally unconditional. The holder burns the token and presents a proof the vault verifies, with no operator to refuse it and no committee to convene. Solvency is structural rather than monitored, for the reasons given in Section~\ref{sec:bridging}, so there is no challenge window during which an unnoticed fraudulent withdrawal could succeed.

\section{Tokenization}

An issued asset on Unicity uses a token type with immutable rules. This structure supports direct holder verification of the properties required for tokenization.

\medskip

A holder must establish issuance authority, compliance with the permitted supply, and a valid transfer history. On a shared ledger, these checks depend on correct contract implementation and execution by the chain. On Unicity, the holder checks them directly against rules fixed in the type definition.

\medskip

Issuer-gated assets use UTS-1. The type pins the issuer's key, and every mint includes a signature verified by the recipient. Splits provide divisibility, with each recipient checking value conservation.

\medskip

Unique items use UTS-2. The genesis commits to immutable content by hash. The content can be stored at any location because the hash authenticates it. Curated collections require issuer signatures for minting; open collections allow anyone to mint, with provenance established at the application layer.

\medskip

Capped supply uses UTS-3. Every valid issuance must consume one member of a bounded set of genesis states, each admitted at most once by the aggregation layer. A recipient verifies compliance with the cap for the received token without observing other issuance or trusting the issuer to respect the cap. Profiles support treasury distribution, independent issuance over time, and supply pre-committed to specific denominations. The cap applies per network; deploying the same definition on a second network does not create a combined cap across both.

\medskip

Compliance requirements are part of the type definition. A regulated instrument can require an attestation from an accredited party at each transfer. Every recipient checks the attestation before acceptance, without requiring public disclosure of the full transfer history or retrospective ledger analysis.

\medskip

Registry metadata carries the display name, symbol, decimals, and icons, none of which are consensus-relevant. Only the frozen definition governs validity, so a misleading display name cannot make an invalid token acceptable.

\section{Decentralized Finance}

Section~\ref{sec:pools} described an automated market maker without an operator. Its rules enforce custody, solvency, and conservation properties through recipient verification.

\medskip

No party has custody of deposited value. Pool reserves are governed by rules rerun by every verifier, with no administrator key, upgrade path, or privileged party. Recipients of pool-derived tokens directly check solvency and conservation. A minimum-output commitment and guaranteed refund path bound a swapper's losses. A hostile party that successfully advances the pool can cancel a trade but cannot confiscate its value.

\medskip

A pool instance serializes operations, limiting its throughput relative to an order book on a fast chain. The party advancing the pool orders the applied operations, permitting reordering within a batch. Verifiers of any pool-produced token can inspect the pool state and every transition, so pool activity lacks the privacy of ordinary transfers.

\medskip

The platform also supports bilateral financial settlement. Atomic swaps between two parties require no venue, and lending can lock collateral under agreed release conditions. Table~\ref{tab:defi-comparison} compares these mechanisms with existing venues.

\section{Agentic Commerce}

Autonomous commerce between agents requires three functions that platforms normally bundle: a way to find a counterparty, a way to agree terms, and a way to settle. Unbundling them lets each be provided competitively.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\textwidth]{img/BulletinBoard.png}
    \caption{Agents interact through a cryptographic bulletin board, using platform functions and specialized service agents rather than a single intermediating platform.}
\end{figure}

\subsection{Discovery}

A cryptographic bulletin board is permissionless infrastructure where agents post intents, meaning signed declarations of what they wish to buy, sell, or exchange. Unlike an order book requiring exact matching, intents express constraints that agents resolve by negotiating. An intent might specify a quantity of a component delivered to a location within a deadline under a maximum price, a quantity of compute at a minimum specification within a price range, a market data feed under a latency bound, or a position on an event.

\medskip

The board provides permissionless posting, cryptographic commitment so that a posted intent cannot be repudiated, optional encryption, and queryable discovery. It helps parties find one another and does not intermediate what follows.

\subsection{Spam Resistance}

Permissionless posting uses economic controls to limit abuse. A posting bond is returned when an intent expires or is fulfilled and forfeited when it is flagged, increasing the cost of sustained spam. Reputation staking requires agents with poor histories to stake more or accept rate limits. Tiered visibility displays established agents broadly while requiring explicit queries for new agents. Recipient filtering lets each agent set thresholds for bond size, reputation, and intent type. Agents with no reputation can be required to make a small payment.

\medskip

These controls can be combined. A typical configuration requires a bond plus reputation from established agents and a bond plus payment from new agents. Spam costs then scale with volume while individual legitimate postings remain inexpensive.

Escrow requires no custodian. Transfer conditions release funds to the seller on confirmed delivery and return them to the buyer otherwise. Both parties can inspect the conditions before committing funds.

\medskip

Reputation is represented by tokens recording transaction history. These tokens can be used across marketplaces and staked when entering an agreement.

\medskip

Fulfillment agents coordinate delivery of physical goods and compete on price, speed, and reliability. Digital goods are delivered immediately through peer-to-peer transfer.

\medskip

Insurance agents assess counterparty reputation and transaction size to underwrite risk under verifiable policy terms.

\subsection{Settlement and Disputes}

Once matching intents are found, the parties negotiate directly and agree which escrow, insurance, and fulfillment providers to use. Settlement is a sequence of transfers under agreed conditions. No platform coordinates the flow.

\medskip

Disputes are adjudicated by arbitration agents that stake tokens as a guarantee of impartiality. A party initiates by posting a bond, which discourages frivolous claims. Both sides submit evidence, the arbitrator issues a signed ruling, and the ruling determines how the escrowed funds are released. Appeals escalate to a panel against a larger bond, and an overturned ruling costs the original arbitrator part of its stake. Arbitrators accumulate reputation through uncontested rulings and can charge accordingly.

\section{Gaming}

Blockchain use in games has largely been limited to asset tokenization within centralized architectures. On-chain game execution is impractical at the required transaction rates and latencies. Decentralized game execution can support ownership of assets usable across titles, transparent and community-governed rules, censorship resistance, and direct payments to creators.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{img/AgenticGaming.png}
    \caption{Game logic as agents. Player agents synchronize directly with one another, with verifiable state transitions proving that the rules were followed.}
    \label{fig:game}
\end{figure}

Client-server architectures limit the number of players that can interact in real time on one server instance. Large simulations therefore cap participation in a shared world. Client-side execution removes this server capacity constraint but requires protection against cheating clients.

\medskip

In Unicity's model, players interact through agents that execute game mechanics. When players encounter one another, their agents synchronize through verifiable state transitions that establish compliance with the rules. Tokens represent player-owned, portable assets. Game logic handles verification failures, for example by reverting to the last state agreed by both parties. Local interactions allow execution to scale: an encounter between two players affects only those participants.

\section{Further Reading}

This paper is an overview. The protocol specification and the formal security arguments summarized here are given in the companion documents.

\medskip

The Yellowpaper~\cite{yellowpaper} specifies the protocol in full: the consensus layer, the certificate framework, the execution layer and its token encoding, governance, the enshrined EVM partition, and bridging. The Bluepaper~\cite{bluepaper} treats the aggregation layer in depth, including the radix tree design, the security model, the formal Zero Knowledge setup and proof of append-only consistency, the AIR arithmetization, the measured performance reported in Table~\ref{tab:perf}, and recursive aggregation.

\medskip

Two academic papers carry the formal results. The execution-layer paper~\cite{exemodel} develops the security model for off-chain execution and proves resistance to double-spending and to blocking, together with service-side privacy and the unlinkable-key protocols of Section~\ref{sec:privacy}. The predicates paper~\cite{predicates} generalizes ownership to programmable spending conditions, proves that those properties survive the generalization, and constructs trustless atomic swaps.

\medskip

The State Transition SDK~\cite{sdk} provides client libraries for token operations.
