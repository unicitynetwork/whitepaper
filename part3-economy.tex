\part{The Machine Economy}\label{part:economy}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Parts~\ref{part:protocol} and~\ref{part:execution} described a settlement platform. This part describes its most demanding users: autonomous programs that transact continuously, at volumes and price points that make per-transaction settlement costs decisive, and that cannot call a bank when something goes wrong.

\section{Agents as Economic Actors}

An \emph{agent}, for the purposes of this paper, is a program that holds tokens, runs on hardware nobody else has to trust, and produces outputs that counterparties accept because they re-verified them rather than because they trusted the program or its operator.

\medskip

That definition is narrower than the word's everyday use and deliberately so. It says nothing about whether the program uses machine learning, and the platform's guarantees do not depend on the answer. An agent that runs a fixed algorithm and an agent that runs a language model are the same kind of participant here: both hold tokens, both satisfy spending conditions, and both produce results their counterparties check. The cryptographic guarantees attach to the settlement, not to the reasoning that led to it.

\medskip

This distinction matters because the two are often conflated. A verifiable payment from an agent proves that the value moved and was not double-spent. It does not prove that the agent was right to send it. Section~\ref{sec:verifiable} in Part~\ref{part:execution} sets out which of an agent's actions can be made verifiable in the strong sense and which cannot.

\section{Identity, Storage, and Mobility}

An agent is defined by its cryptographic identity and its verification logic, not by the machine it runs on. Three properties follow, and together they are what allow an agent to be a durable economic participant rather than a process on someone's server.

\begin{description}
    \item[Addressing without location.] Agents address one another by self-authenticating identifiers rather than by network address. An agent can move from a server in one jurisdiction to a laptop in another without interrupting its ability to be reached, to be paid, or to transact.

    \item[Storage without a host.] An agent does not depend on a host filesystem for the state that matters. Its assets and its history live in tokens, which are portable, self-verifying, and meaningful to anyone. Tokens are the agent's durable storage, and moving the agent means moving them.

    \item[Execution without trust in the host.] A host supplies processor cycles and bandwidth. It does not supply correctness, because correctness is established by the recipient re-checking the result. Signing keys are held in a hardware security module or a secure enclave so that a hostile host cannot impersonate the agent it is running.
\end{description}

The consequence is censorship resistance of a practical kind. An agent that is shut down at one host resumes at another from its last verifiable state, because that state is in tokens rather than in the host's disk. There is no registry to be removed from and no address to be blocked.

\section{Agent-to-Agent Payments}

Machine payments differ from human payments in three ways that matter for infrastructure, and each of them is a problem for per-transaction settlement.

\medskip

\textbf{They are frequent.} A program metering an API call, buying a second of compute, or settling a data feed transacts at a rate no human does. On a network that charges per transaction, that frequency is itself the cost, and it grows without bound.

\medskip

\textbf{They are small.} Paying a fraction of a cent for a single inference or a single request only works if settlement costs a small fraction of that. Once a fee approaches the value transferred, the transaction stops making sense, and an entire category of machine commerce with it.

\medskip

\textbf{They are budgeted in advance.} An autonomous program is given a spending limit by its operator. It cannot renegotiate that limit because an unrelated network became busy. A fee that varies with someone else's demand is not something an agent can plan around.

\medskip

Unicity's model addresses all three at once. Settlement capacity is bought as a subscription rather than per transaction, so volume does not change cost. The marginal cost of an additional transfer is close to zero, because there is no block space to auction and no shared state to contend for. And because the fee does not float with congestion, an operator's budget means what it says.

\medskip

Two further properties matter specifically for agents. Transfers are private to the parties, so an agent's trading pattern, counterparties, and balances are not published to competitors by default. And verification is cheap enough that an agent receiving a payment can validate it completely, in-process, without an external service in the path.

\section{Payments Inside Web Requests}

Most agent interactions are ordinary web requests. A client asks a service for something, and the service wants to be paid. The conventional approach to metering these has been to attach a blockchain settlement flow to the request, which introduces a facilitator to observe the payment, a chain to record it, and a settlement wait before the service can safely respond.

On Unicity the payment is the message. A token is self-validating, so a client can attach one to the request itself, and the service establishes that it has been paid by verifying what it received. There is no facilitator to observe the transaction, no public record of it, and no settlement round trip between receiving the request and answering it. The steps that exist to reconcile a payment against an external ledger are not optimized away; they have nothing to do, because there is no external ledger holding the balance.

\section{The Infrastructure Marketplace}

An economy of autonomous programs needs physical infrastructure, and the platform provides a way for that to be supplied competitively rather than by a single provider. Participants earn the native currency by offering resources that agents consume.

\begin{itemize}
    \item \textbf{Compute hosts} run agent workloads, supplying cycles without being trusted for correctness.
    \item \textbf{Relay operators} provide bandwidth and routing for the overlay through which agents reach one another.
    \item \textbf{Storage providers} pin and serve the data agents reference, including the content that non-fungible tokens commit to by hash.
    \item \textbf{Aggregator operators} run the shards, funded by the subscription gateway described in Part~\ref{part:protocol}.
    \item \textbf{Provers} produce the recursive aggregate proof and, where applications use them, the succinct proofs behind compression and bridge redemption. This role is permissionless and requires no privileged position.
    \item \textbf{Gateway operators} connect agents to conventional web services and to legacy payment systems.
\end{itemize}

None of these roles is trusted for correctness. Each supplies a resource whose correct use is established by proof or by the recipient's own verification, which is what allows the supply side to be open.

\section{The Agent Platform}

Unicity also develops a security and runtime stack for AI agents, comprising the Semantic Intercept Fabric for policy enforcement below the model, the Astrid agent operating system for sandboxed execution with auditing and budget enforcement, and associated components for discovery and orchestration. Those systems address a different problem from the one this paper describes, namely constraining what an agent does rather than settling what it owes, and they are documented separately. The settlement platform does not depend on them, and agents built on any framework can use it.
